PHASE 2 — IMPLEMENT ONLY IF SAFE CONTRACT EXISTS
==================================================

If the existing backend already provides a safe server-authoritative customer order flow that supports the mobile requirements, migrate mobile checkout to that existing flow.

DO NOT modify the backend unless a genuine contract gap is proven.

The preferred behavior is:

Customer selects cart items
        ↓
Mobile sends product IDs + quantities + required checkout data
        ↓
Backend validates authenticated customer
        ↓
Backend validates products and stock
        ↓
Backend calculates authoritative prices
        ↓
Backend calculates authoritative totals
        ↓
Backend calculates delivery/fees where applicable
        ↓
Backend creates order transactionally
        ↓
Mobile receives authoritative order result
        ↓
Mobile clears only successfully purchased cart items
        ↓
Mobile invalidates/refetches orders
        ↓
Navigate to order details/success

NEVER trust client-provided:
- unit prices
- subtotal
- total
- delivery fee
- discount amount
- final order amount

If the current API accepts those fields, they must NOT be treated as authoritative by the mobile client.

==================================================
DUPLICATE ORDER PROTECTION
==================================================

Implement client-side protection against accidental duplicate submissions.

Requirements:

1. Disable the checkout submit action while the request is actively processing.

2. Prevent double taps.

3. Generate a unique checkout attempt/idempotency identifier if the existing backend contract supports such a mechanism.

4. If the backend does NOT support idempotency keys, DO NOT invent a fake backend contract.

Instead:
- inspect whether an existing safe reconciliation mechanism exists
- prevent repeated submissions while the same checkout request is in flight
- safely handle network timeout/retry
- determine whether an order may already have been created before retrying

5. NEVER blindly retry an order-creation request after a timeout if doing so could create a second order.

6. If the backend returns an order ID successfully, treat that order as the source of truth.

7. If the request times out after possible server processing, show a safe recovery state instead of automatically creating another order.

Example recovery:

"Your order may already have been submitted. Checking your orders..."

Then query the customer's orders/reconciliation endpoint if the existing API supports this.

==================================================
MULTI-MALL CHECKOUT
==================================================

Inspect how the current cart handles products from multiple malls.

If the backend requires one order per mall:

- split the checkout safely
- never create orders sequentially without recovery logic
- record successful order IDs
- record failed/pending attempts
- do not lose successful orders
- do not duplicate successful orders on retry
- provide a clear recovery state to the user

If the backend already supports multi-mall checkout transactionally:

- use that existing behavior
- do not recreate the logic on mobile

DO NOT guess.

==================================================
CART USER ISOLATION
==================================================

Audit the current AsyncStorage/Zustand cart persistence.

The cart must NOT leak between different authenticated users on the same device.

Implement safe user scoping.

Preferred behavior:

user A login
→ cart belongs to user A

logout
→ user A cart is cleared or safely detached

user B login
→ user B must never see user A cart

If using persisted storage keys, ensure the authenticated user identity is part of the persistence strategy OR safely clear/reinitialize cart state on account changes.

Also handle:
- login
- logout
- token expiration
- account switching
- app restart

Do not expose another user's cart.

==================================================
ORDER CACHE / STATE
==================================================

After successful order creation:

- invalidate/refetch customer orders
- invalidate relevant cart queries if applicable
- update local cart only after confirmed successful order creation
- do not clear the entire cart if only part of it was successfully ordered
- preserve failed/unsubmitted items where appropriate

Use the existing React Query/Zustand architecture.

Do not introduce another state-management system.
