# SmartMall Mobile — Phase 3

## Cart + Checkout + Customer Orders

Phase 2 is complete and verified.

Now implement **Phase 3 only** for the independent SmartMall mobile application.

### 1. STRICT SCOPE

Work only inside:

`/mobile`

Do NOT modify:

* `/frontend`
* `/backend`
* Laravel routes
* Laravel controllers
* migrations
* database schema
* seeders
* existing Capacitor application
* production website behavior
* owner/admin interfaces

Do not start Phase 4.

Do not add scanner, push notifications, complaints, delivery features, payment gateway, WhatsApp ordering, or native Google OAuth in this phase.

Before changing anything, inspect only the existing `/mobile` implementation created in Phase 1 and Phase 2 and reuse its existing architecture.

---

# 2. PHASE 3 OBJECTIVE

Add a professional mobile shopping flow:

**Product → Cart → Checkout → Order Created → Order Details → Orders History**

The experience must feel like a real standalone shopping application, not a WebView.

---

# 3. CART

Create a proper mobile Cart screen.

Requirements:

* Add product to cart.
* Increase quantity.
* Decrease quantity.
* Remove item.
* Clear cart.
* Show product image.
* Show product name.
* Show unit price.
* Show quantity.
* Show line total.
* Show cart subtotal.
* Show total item count.
* Empty-cart state.
* Loading states where necessary.
* Error states.
* RTL/LTR support.
* Arabic and English translations.
* ILS / ₪ formatting.

Use the existing Zustand architecture where appropriate.

Cart state may be persisted locally, but do not store authentication tokens in persisted Zustand state.

Do not create a server-side cart because Phase 3 should work with the existing API contract.

---

# 4. PRICE AND STOCK SAFETY

Never trust locally stored prices or totals when creating an order.

The mobile application may use local cart data for display, but before final order creation:

* Refresh/validate product information where necessary.
* Use the existing backend order API if available.
* Send product IDs and quantities rather than trusting client-calculated totals.
* Never allow the client to override price.
* Never allow the client to override stock.
* Display the server-authoritative result.

If the current backend does not expose a suitable order-creation endpoint, DO NOT modify the backend automatically.

Instead:

1. Inspect the existing API.
2. Identify the correct existing endpoint if available.
3. If no safe existing endpoint exists, document the exact backend API gap.
4. Do not invent a fake successful order.
5. Do not modify Laravel in this phase.

---

# 6. ORDER CREATION

Implement the real order creation flow using the existing SmartMall API.

Requirements:

* Prevent duplicate submissions.
* Disable submit while processing.
* Handle network failures.
* Handle validation errors.
* Handle authentication expiration.
* Handle insufficient stock.
* Handle changed product prices.
* Handle server errors.
* Never show "Order successful" unless the server confirms creation.

After successful creation:

Navigate to:

`/order/[id]`

and show the created order.

Clear the cart only after confirmed successful order creation.

# 11. API ARCHITECTURE

Continue using the centralized API layer from Phase 2.

Screens must NOT contain raw Axios requests.

Create/reuse dedicated API functions such as:

* cart-related local actions
* order creation
* orders list
* order detail

Use TanStack Query for server state.

Use proper query invalidation after order creation.

Keep API types centralized.

Do not duplicate API logic between screens.

---

# 12. AUTHENTICATION

Continue using the existing Phase 2 authentication system.

Use:

* Expo SecureStore on native.
* Existing session handling.
* Existing centralized 401 handling.

Never put tokens in:

* URLs
* logs
* AsyncStorage
* persisted Zustand state

If the session expires during checkout:

* stop the operation safely.
* preserve the user's local cart where possible.
* redirect to login.
* after successful login, allow the customer to continue.

---

# 14. PERFORMANCE

Keep the application scalable.

Do NOT:

* load unnecessary full product catalogs.
* request all orders without pagination if pagination exists.
* repeatedly fetch the same product data.
* perform expensive calculations on every render.
* create unnecessary global state.
* persist large server responses locally.

Use React Query caching appropriately.

Use stable query keys.

Avoid unnecessary rerenders.

---

# 15. ERROR HANDLING

Every important operation must handle:

* Offline/network failure
* 401
* 403
* 404
* 422 validation errors
* 409/conflict if returned
* 429/rate limiting
* 500/server error
* insufficient stock
* changed price
* invalid product
* empty cart

Display user-friendly Arabic/English messages.

Never expose raw server errors to customers.
